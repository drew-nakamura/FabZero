## Immediate handoff sequence

1. We will provide one actual accepted N=8 app handoff ZIP. Your two existing implementation manifests are already on `drew-branch`; compare the ZIP's kernel and wrapper hashes, N/LANES, part, clock and bitstream hashes against them.
2. Add `inputs.json`/parent linkage and adapt the hardware result to the app's versioned signed schema, or add a trusted adapter that reads and verifies your raw files then signs the app envelope. Keep the signing secret outside Git and JSON.
3. Run the archived parent vectors on the board, including initial, repeat-without-reload and reset-recovery outputs. Confirm cycle counts and hashes against that parent. Your identity-vector runs are valuable board evidence but cannot be linked to an unrelated app run.
4. Import the signed result into the app and rehearse the recorded demo. Show the implementation report metrics only after binding them to the same bitstream.

**Other assumptions to resolve:** The existing implementation uses `pl_clk0` at 99,999,001 Hz, whereas the draft app schema example says 100,000,000 Hz; use the manifest's actual configured value consistently. Confirm the exact Vivado part and address map from the real block design.

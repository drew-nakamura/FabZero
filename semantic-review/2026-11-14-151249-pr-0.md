# Imported KV260 board evidence and evidence-first demo pipeline

This change adds a fallback board-result import path that validates a physical runner report against an immutable RTL run, persists it as a child, and renders it separately in the demo. It also restructures the page around direct controls, a six-stage evidence pipeline, handoff export, and explicit simulation-versus-physical labels. The arithmetic, parent linkage, source/input hashes, compiled parameters, and cycle count are checked deterministically, but the current trust boundary does not prove that the uploaded JSON came from the fixed runner or that its implementation claims are backed by the named manifest. **Watch for:** **confirmed, P1** forgeable `board_measured` promotion; **confirmed, P1** unverified implementation and lifecycle claims; **likely, P2** concurrent retry failures; **confirmed, P2** an undefined cross-runner output-hash encoding; and **confirmed, validation gap** the UI regression suite could not run because Node is unavailable.

**Verdict**: NEEDS_CHANGES

## High-level view

The new endpoint keeps simulation and board evidence as separate parent and child records, and it fails closed on arithmetic or identity mismatches. The central **confirmed** trust gap is that a same-origin or local caller can submit a self-authored JSON document containing the already-known parent outputs and receive `physical_fpga: true`; no runner credential, signature, artifact registry, or operator-attestation state distinguishes trusted runner output from an arbitrary import.

The implementation fields are syntactically validated but not substantively bound. A **confirmed** caller-provided manifest digest, part string, clock, and `timing_met: true` are enough to create a measured kernel duration and a passed implementation stage, although the specification says the manifest must bind reports, sources, bitstream, part, parameters, and clock. The result schema also has no evidence for the required repeat-without-reload and reset/recovery checks.

Persistence uses a child run, a unique runner-result index, and a single transaction for the run, index, and event. The **likely** remaining idempotency gap is the separate read-before-insert sequence: two simultaneous retries can both observe no row, after which one request hits the uniqueness constraint and returns 502 rather than the already-created result.

A **confirmed** integration gap remains in the undocumented serialization used for `output_sha256`; an external Windows runner must reproduce Python’s default `json.dumps(outputs)` bytes exactly, including separators, even though the contract specifies only a SHA-256 value.

<details><summary>Details</summary>

## Uploaded JSON can mint physical evidence without runner provenance

**Confirmed, P1.** `POST /api/runs/<id>/board-result` accepts any JSON request that passes value checks, and the only request-origin control is the existing browser Origin check. `validate_result` proves that the submitted outputs, inputs, source labels, parameters, and cycles agree with the parent, but every required value is available from the parent report or can be chosen by the submitter. The endpoint does not verify a runner signature, short-lived job token, allowlisted artifact ID, registered runner identity, or an explicit operator attestation before setting `evidence: board_measured`, `physical_fpga: true`, and `correct: true` (`server.py:95-123`, `siliconos/board.py:79-232`).

Loopback binding limits remote exposure but does not establish provenance for a manually selected file or another local process. The UI then labels the child “Recorded KV260 board measurement” and marks the implementation and board stages passed (`web/app.js:11,27-30`). Require an authenticated or signed result from the fixed runner and bind it to a server-issued job and allowlisted artifact. If manual import must remain unsigned for the fallback, persist it under an explicit unverified/imported evidence state until a human or trusted runner verification step promotes it.

## Manifest and clock claims are accepted without the artifact package

**Confirmed, P1.** The validator checks only that `implementation_manifest_sha256` and `bitstream_sha256` look like lowercase digests, `target_part` and `vivado_version` are nonempty strings, and `timing_met` is exactly true (`siliconos/board.py:113-130`). It never receives or hashes the manifest, parses report hashes, verifies the exact installed part against an artifact registry, or demonstrates that the bitstream, source, top, N/LANES, and configured clock belong to one implementation. Despite that, normalization copies `timing_met: true`, sets `physical_fpga: true`, and derives `measured_kernel_ns` from the asserted clock (`siliconos/board.py:181-223`). This directly conflicts with the authoritative rule that a timing boolean alone is insufficient and timing remains unknown until the manifest binding is verified (`docs/DEMO_PRODUCT_AND_FPGA_SPEC.md:525-531`).

Accept the implementation manifest or resolve its digest through an allowlisted local registry, hash it server-side, parse and match its report/source/bitstream/part/top/parameter/clock bindings, and preserve timing as unknown until those checks pass. The configured frequency also needs evidence that it is the actual board clock before the server emits a field named `measured_kernel_ns`.

## Required board lifecycle checks have no schema representation

**Confirmed, P1.** The physical acceptance contract requires a repeat without reloading and reset/reload recovery (`docs/DEMO_PRODUCT_AND_FPGA_SPEC.md:632-634,1039-1044`), but the board-result envelope and validator describe only one output vector, one cycle count, and identity/N/LANES reads. A single-run payload therefore becomes `board_measured` even when the runner never performed the required lifecycle checks (`siliconos/board.py:132-232`).

Extend the signed or trusted result with structured lifecycle outcomes and their captured outputs/cycles, then validate them against the same oracle and expected schedule. Until that evidence exists, the child can record one physical arithmetic observation but should not satisfy the full board-verification acceptance gate.

## Concurrent retries can break idempotency

**Likely, P2.** The endpoint queries `board_results` for `runner_result_id`, returns the stored child when found, and otherwise inserts the new run and index (`server.py:110-121`). Under `ThreadingHTTPServer`, two requests for the same new runner ID can both complete the query before either insert commits. One transaction then wins and the other raises a SQLite uniqueness error, which falls through to the generic 502 response instead of returning the winner’s child.

Use one transaction with `INSERT ... ON CONFLICT`/`INSERT OR IGNORE`, then read and compare the stored payload hash, or catch the uniqueness conflict and perform the same comparison. Add a synchronized concurrent-request test; the current test covers only sequential replay (`tests/test_board.py:144-163`).

## Output hash bytes are not defined for the Windows runner

**Confirmed, P2.** Board acceptance hashes `json.dumps(outputs).encode()` using Python’s default separators (`siliconos/board.py:165-168`), while the public contract says only to recompute `output_sha256` and gives no canonical byte encoding (`docs/DEMO_PRODUCT_AND_FPGA_SPEC.md:497-520`). A runner that hashes packed signed INT32 values, UTF-8 JSON without spaces, or pretty-printed JSON will be rejected even when every uploaded output passes the independent oracle.

Specify the canonical serialization in the contract and runner instructions, preferably a versioned byte format or canonical compact JSON, and use the same shared helper for simulation, handoff, board validation, and runner code. Add a fixed digest vector so the Windows owner can verify compatibility before board bring-up.

## Regression coverage and execution limits

**Confirmed, validation gap.** The Python suite passed 61 tests and `git diff --check` passed, but the JavaScript UI suite did not execute because `node` is unavailable. The new pipeline, import, history, and stale-board transitions therefore remain unverified here. Run `node --test tests/test_web.js` before merge, and add coverage for changing the active specification after a board import and inspecting a board child from history with no parent selected.
